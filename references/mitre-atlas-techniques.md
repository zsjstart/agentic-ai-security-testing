# MITRE ATLAS Technique Checklist (by OWASP ASI Category)

MITRE ATLAS (Adversarial Threat Landscape for Artificial-Intelligence Systems, atlas.mitre.org) is a living knowledge base of adversary tactics and techniques against AI-enabled systems, maintained by MITRE and modeled after ATT&CK.

**Source of this file:** built directly from the official ATLAS dataset, fetched from the `mitre-atlas/atlas-data` GitHub repository (`dist/v6/ATLAS-2026.09.yaml`) — **content version 2026.09** (published 2026-09-15): 16 tactics, 120 techniques, 88 sub-techniques (208 combined entries). Of these 208 entries, **146 are judged relevant to LLM/agentic-application security testing and are cited individually below.** The other 62 are deliberately excluded — they are classic-ML/CV-specific techniques (e.g. physical adversarial patches, image-classifier evasion, structured-data model attacks) or generic infrastructure/lifecycle techniques with no AI-specific mechanism that would change how this skill's Phase 3 tests are designed. That exclusion is a curatorial judgment made explicit here, not a silent gap: this file is a *relevant-subset checklist*, not a reproduction of the full ATLAS catalog, and a reader should treat any ID not listed below as "considered and excluded as out of scope for this skill," not "overlooked." Every ID/name/description below was read directly out of the structured ATLAS data, not recalled or inferred, and every condensed description is derived from that same source's own technique description field.

**On this file's scope expansion (2026.08 → 2026.09 pull, September 2026):** an earlier version of this file cited only 52 of ATLAS's techniques/sub-techniques (44 parents + 8 sub-techniques). A subsequent audit read every one of ATLAS's then-197 official entries' *full* description text — not a keyword or title match — and cross-checked each candidate against `references/owasp-agentic-top10.md`'s actual ASI01-10 definitions (not a generic "sounds AI-related" heuristic) to decide relevance. That audit found 86 additional techniques genuinely relevant to LLM/agentic-application security testing that the original build had missed, and also found the original file had failed to break out several techniques' sub-techniques individually even where the parent was already cited (T0051, T0010, T0080, T0084, T0052 all had un-cited sub-techniques). Separately, ATLAS's 2026.09 release (published 2026-09-15, newer than the 2026.08 snapshot the original audit used) added 11 further entries, all judged relevant to this skill. The combined, corrected result is the 146-entry catalog below — a deliberate, rigorous expansion driven by a full-text audit methodology, not scope creep or casual addition.

**Purpose in this skill:** OWASP's Top 10 for Agentic Applications (`owasp-agentic-top10.md`) gives the category-level failure mode ("what can go wrong"). This file adds the specific, named attack technique underneath each applicable category ("how an adversary actually does it") — a coverage checklist for Phase 3 test design, so a test plan isn't considered complete after proving a category's mechanism with just one technique. See SKILL.md Phase 3 for how this is used.

**Freshness warning:** ATLAS is actively updated. Re-check `https://github.com/mitre-atlas/atlas-data` (or atlas.mitre.org) for a newer `dist/v6/ATLAS-<latest>.yaml` before citing an ID in a report more than a few months old relative to this file's 2026.09 version. Tactic names occasionally get renamed (e.g. an earlier release's "AI Attack Staging" tactic is this release's "AI Attack Adaptation") — cite the technique ID, not the tactic name, as the stable identifier.

**A note on technique IDs vs. sub-technique IDs:** ATLAS IDs of the form `AML.TXXXX` are parent techniques; `AML.TXXXX.YYY` are sub-techniques nested under a parent. Below, a sub-technique is nested as an indented bullet under its parent whenever they share the same primary OWASP category. Where a sub-technique's own primary category differs from its parent's (this happens — a sub-technique can have a materially different mechanism from its siblings), it is instead listed as its own top-level bullet in its own primary category, with a note pointing back to the parent (cited elsewhere in this file). This is noted individually at each such entry rather than silently nesting it somewhere it doesn't belong.

## ASI01 — Agent Goal Hijack

- **AML.T0051 — LLM Prompt Injection** (tactic: Execution). "An adversary may craft malicious prompts as inputs to an LLM that cause the LLM to act in unintended ways." Has direct and indirect variants — maps onto the Direct Injection vs. Web/Document/RAG/Template Injection channel split.
  - **AML.T0051.000 — Direct** (tactic: Execution). The adversary injects the malicious prompt as the user of the LLM directly, to gain a foothold or misuse the LLM's own output (e.g. generate harmful content).
  - **AML.T0051.001 — Indirect** (tactic: Execution). The malicious prompt arrives via a separate ingested data channel (document, email, database, website) rather than from the user — this is the specific sub-ID for the "hidden instructions in retrieved/uploaded content" pattern this skill's entry-point registry tests directly (document upload, RAG, web-fetch tools). Often paired with obfuscation (AML.T0068) to stay invisible to a human reviewer.
  - **AML.T0051.002 — Triggered** (tactic: Execution). The malicious instruction is dormant until a future user action or system event fires it — the sub-ID for delayed/conditional injection payloads (e.g. "if the user asks about X, do Y"), relevant to multi-turn and event-driven agent testing.
- **AML.T0054 — LLM Jailbreak** (tactic: Privilege Escalation, Defense Evasion). Inducing an LLM to ignore/circumvent/override its safety alignment or guardrails — distinct mechanism from prompt injection (bypassing trained behavior vs. overriding stated instructions). The 2026.09 description catalogs many distinct strategies (instruction override, roleplay/persona switching, fictionalization/hypotheticals, multi-turn "Crescendo" escalation, constrained-output-format coercion, data-structure injection to hijack tool schemas, obfuscation/encoding, "high priority objective" framing, and affirmation-priming) plus algorithmic/automated jailbreak generation and direct weight-level "abliteration" of open-weight models — a test plan should sample more than one framing family, not just one persona trick.
- **AML.T0093 — Prompt Infiltration via Public-Facing Application** (tactic: Initial Access, Persistence). Malicious prompts introduced via a public-facing surface (a web page, an upload, email, ticketing systems like Jira, or OCR-mediated infiltration via images/screenshots/invoices) with the intent of later ingestion by an AI system — the direct ATLAS counterpart to indirect hijack via retrieved/uploaded content.
- **AML.T0100 — AI Agent Clickbait** (tactic: Execution). Deceptive web content crafted to bait a computer-using AI agent or AI browser into unintended actions (clicking, copying code, navigating) — a distinct sub-pattern specific to browsing/computer-use agents, separate from a passive text-injection payload; may itself carry an indirect prompt injection.
- **AML.T0094 — Delay Execution of LLM Instructions** (tactic: Defense Evasion). An instruction embedded now but designed to trigger on a future event/keyword/interaction, specifically to bypass turn-scoped defenses that only inspect the current conversation turn for untrusted-data markers — relevant to multi-turn goal-drift and context-window-pressure scenarios.
- **AML.T0092 — Manipulate User LLM Chat History** (tactic: Defense Evasion). Covering tracks of a prior hijack by altering what the user/model can see of past turns; notes that desktop chat clients often only render history once per session open, letting manipulation go unnoticed.
- **AML.T0068 — LLM Prompt Obfuscation** (tactic: Defense Evasion). Hiding or encoding a prompt injection/retrieval-content payload to evade detection by humans or guardrails — includes text rendering tricks (tiny/invisible/background-colored text, hidden HTML), multimodal variants (low-contrast text in images, faint or sped-up audio, single-video-frame text), and encoding schemes (base64, rot13).
- **AML.T0073 — Impersonation** (tactic: Defense Evasion). Impersonating a trusted person/organization (executive, colleague, vendor) to persuade a target — human or agent — into an action; the description also flags AI DevOps supply-chain targets (model repos, container registries, software registries) as impersonation targets. Secondary category: cross-referenced under ASI09 below (impersonation applied to a human reviewer rather than the model).
- **AML.T0078 — Drive-by Compromise** (tactic: Initial Access). An AI agent retrieving/browsing a web page (on a user's behalf or during its own normal operation) that contains a prompt injection — the specific "malicious web page as delivery mechanism" variant of indirect goal hijack, distinct from a poisoned document or RAG entry.
- **AML.T0056 — Extract LLM System Prompt** (tactic not resolved in this file's source pull — verify against the live matrix). Extracting an LLM's system prompt via injection or from a leaked configuration file, to reverse-engineer its guardrails and craft better-targeted injection/jailbreak payloads.
- **AML.T0061 — LLM Prompt Self-Replication** (tactic: Persistence). A carefully crafted injection designed to cause the LLM to reproduce the prompt itself as part of its output, letting the payload propagate to other LLMs/agents and persist on the system — a documented "prompt injection worm" pattern, typically paired with a jailbreak or data-leakage payload. Secondary category: cross-referenced under ASI07 below (propagation across multiple agents).
- **AML.T0134 — AI Targeted Cloaking** *(2026.09 addition)* (tactic not resolved in this file's source pull — verify against the live matrix). Delivering different content to an AI crawler/browser/agent (detected via user-agent) than to human visitors or conventional security scanners, so a prompt-injection payload is invisible to anyone not using the same AI client — often combined with Drive-by Compromise (AML.T0078). Directly relevant to any test of web-fetch/browsing tools that only crawls with a human-like or generic scanner user-agent, since it would miss this payload class entirely.
- **AML.T0131 — Crafted AI Assistant Links** *(2026.09 addition)* (tactic: Initial Access). A link that pre-populates and sometimes auto-submits an attacker-chosen prompt into a target's AI assistant via URL parameters (e.g. `?q=` or `?prompt=`), disguised as a "Summarize with AI" button or share link — the interaction then runs in the target's own authenticated session with whatever access that session has, making it a one-click hijack vector distinct from AML.T0100's UI-bait framing.
- **AML.T0129 — Triggers in Multimodal Inputs** *(2026.09 addition)* (tactic not resolved in this file's source pull — verify against the live matrix). Instructions hidden in a non-text channel of a multimodal input (image, audio, video, or file metadata such as EXIF/ID3 tags) that the model still parses even though text-only moderation/filtering never inspects that channel — a specific, testable gap for any agent accepting image/audio/video uploads whose guardrails are text-only.
- **AML.T0123 — Obfuscated Files or Information** (tactic: Defense Evasion). Broader than T0068: encoding/encrypting content specifically to evade AI-enabled defensive systems themselves — malware classifiers, content filters, secret scanners, automated review — where a downstream tool or compromised system later decodes/assembles the payload. Relevant when the target has its own AI-based input filter to test evasion against, not just the primary LLM's guardrails.
- Upstream/staging steps, not standalone live tests: **AML.T0065 — LLM Prompt Crafting** (tactic: Resource Development) — iterating a prompt until it reliably bypasses the target's defenses; **AML.T0043 — Craft Adversarial Data** (tactic: AI Attack Adaptation) — the general adversarial-input-crafting technique underlying injection/jailbreak development, with a **AML.T0043.003 — Manual Modification** sub-technique (tactic: AI Attack Adaptation) for hand-tuned trial-and-error payload crafting, directly mirroring how a human tester iterates a jailbreak or injection string; and **AML.T0069 — Discover LLM System Information** (tactic not resolved in this file's source pull — verify against the live matrix) — reconnaissance of an LLM's delimiters, keywords, and system prompt to inform payload design, with three sub-techniques: **AML.T0069.000 — Special Character Sets** (delimiters used to separate context from instructions, exploitable to confuse the model about what's "trusted"), **AML.T0069.001 — System Instruction Keywords** (function/tool names discoverable via probing, exploitable to trigger unintended tool calls — secondary category ASI02, cross-referenced below), and **AML.T0069.002 — System Prompt** (discovering the system prompt itself, distinct from T0056's extraction-as-an-attack framing in that this is the staging/discovery step).
- Standalone sub-technique of AML.T0084 (cited under ASI04) whose own mechanism is goal-hijack-specific: **AML.T0084.002 — Activation Triggers** (tactic not resolved in this file's source pull — verify against the live matrix). Discovering the keywords/events (an incoming email, a document add, a message) that activate an agent — the precise staging step behind AML.T0094's delayed/triggered injection and behind unauthenticated peer-triggering in ASI07 scenarios. Secondary category: cross-referenced under ASI07 below.

**Cross-references from other categories:** none of ASI01's own techniques have a *different* primary category, so there are no incoming cross-references to list here beyond what's already inline above.

## ASI02 — Tool Misuse & Exploitation

- **AML.T0053 — AI Agent Tool Invocation** (tactic: Execution, Privilege Escalation). General technique for using access to an AI agent to invoke tools it has access to, toward an end the caller wasn't meant to reach. The current description also flags OS-level invocation paths (deep links, app-intent URIs, universal links, redirect chains) that can open or trigger an installed application even when it isn't a directly configured agent tool, potentially bypassing normal user-confirmation flows.
- **AML.T0086 — Exfiltration via AI Agent Tool Invocation** (tactic: Exfiltration). A tool capable of write/network operations invoked to move data to an adversary, e.g. by encoding sensitive data into a tool's input parameters (email, document edit, CRM update, generated media). The invoked tool may itself be legitimate and merely abused via prompt injection, or may be a poisoned tool (AML.T0110).
- **AML.T0101 — Data Destruction via AI Agent Tool Invocation** (tactic: Impact). A mutative tool invoked to destroy data/files — directly relevant to any destructive-tool-with-insufficient-authorization scenario.
- **AML.T0011.002 — Poisoned AI Agent Tool** (tactic: Execution; standalone — sub-technique of AML.T0011, "User Execution," cited under ASI05, but its own mechanism is tool-invocation-time, so it is listed here instead). A victim invokes a tool that's been tampered with, exposing the agent to poisoned definitions/responses or malicious implementation logic at invocation time. Registration-time root cause overlaps with ASI04 (cross-referenced there); the invocation-time *effect* is what makes it relevant here too.
- **AML.T0011.003 — Malicious Link** (tactic: Execution; standalone — sub-technique of AML.T0011, cited under ASI05). Explicitly calls out an AI agent that fails to validate a website's origin header, accepting connections from any site and thereby letting an adversary reach otherwise-inaccessible networks via a link the agent is induced to click/fetch. Secondary category: cross-referenced under ASI09 below (the social-engineering delivery angle).
- **AML.T0077 — LLM Response Rendering** *(newly cited — was previously an undiscovered gap)* (tactic: Exfiltration). A concrete, well-documented exfiltration technique: inducing the LLM to embed private data into a markdown/HTML image tag or link preview pointing at an attacker-controlled server; when the client auto-renders it (no user click required), the data leaks via the request's query parameters. Significant because it requires no explicit "tool call" in the traditional sense — the exfiltration channel is the response-rendering pipeline itself, relevant to any chat client or agent integration (Slack, Teams) that auto-renders markdown/HTML in responses.
- **AML.T0085 — Data from AI Services** (tactic not resolved in this file's source pull — verify against the live matrix). Using access to an organization's AI-enabled service to collect data the agent can reach via its tools/RAG but a regular user could not reach directly — the general "AI service as confused-deputy data-collection vector" technique.
  - **AML.T0085.000 — RAG Databases** (tactic: Collection). Prompting the service to pull bulk data from its RAG store — potentially the majority of an organization's internal documents. Secondary category: cross-referenced under ASI06 below.
  - **AML.T0085.001 — AI Agent Tools** (tactic: Collection). Prompting the service to invoke its tools to retrieve data from connected APIs the user wouldn't otherwise reach.
- **AML.T0126 — Automated Collection** (tactic: Collection). Scripted/automated bulk collection via agent tools (or command interpreters) rather than one item at a time — a weaker, more generic fit, but directly ties to tool-mediated over-collection at scale (models, datasets, configs, conversation histories, logs).
- Standalone sub-technique of AML.T0069 (cited under ASI01) whose secondary category lands here: **AML.T0069.001 — System Instruction Keywords** — discovering function/tool-name keywords exploitable to confuse the model into invoking tools it shouldn't. Already described under ASI01; noted here because it's staging specifically for tool-misuse scenarios.

**Cross-references from other categories:** **AML.T0010.005 — AI Agent Tool** (primary ASI04, below) — the supply-chain-compromised-tool angle on the same tool surface tested here at the invocation level. **AML.T0110 / AML.T0110.000 / AML.T0110.001** — AI Agent Tool Poisoning and its sub-techniques (primary ASI04, below) — poisoning is the registration-time root cause of many of this category's invocation-time effects.

## ASI03 — Identity & Privilege Abuse

- **AML.T0098 — AI Agent Tool Credential Harvesting** (tactic: Credential Access). Using access to an AI agent to retrieve credentials via the agent's own tools — document stores (SharePoint/OneDrive/Google Drive), code repos (GitHub/GitLab), productivity tools (email, Slack), or local notetaking apps.
- **AML.T0083 — Credentials from AI Agent Configuration** (tactic: Credential Access). Reading credentials for other tools/services directly out of an AI agent's own configuration — API keys, tokens, connection strings that are often placed in less-protected locations for deployment convenience rather than a dedicated secrets manager.
- **AML.T0082 — RAG Credential Harvesting** (tactic: Credential Access). Credentials inadvertently indexed into a RAG store from internal documents, retrieved via the LLM.
- **AML.T0012 — Valid Accounts** *(newly cited)* (tactic: Initial Access, Lateral Movement, Privilege Escalation). Abusing compromised credentials — usernames/passwords or API keys — as a means of gaining initial access to AI resources and services, then using that access to discover further AI artifacts or reach elevated write access to artifacts used in development/production.
- **AML.T0091 — Use Alternate Authentication Material** *(newly cited)* (tactic not resolved in this file's source pull — verify against the live matrix). Using stolen password hashes, tickets, or application access tokens to move laterally and bypass normal access controls; the description explicitly notes AI services commonly use alternate authentication material — tokens, not passwords — as their *primary* access mechanism, making this a directly relevant identity vector rather than a generic one.
  - **AML.T0091.000 — Application Access Token** (tactic: Lateral Movement). Stolen application access tokens used in lieu of login credentials — explicitly ties this to AIaaS access: chatbots, LLM APIs, predictive inference endpoints.
  - **AML.T0091.001 — Web Session Cookie** (tactic: Lateral Movement). Stolen session cookies used to authenticate as another user, potentially bypassing MFA since the session is already authenticated — explicitly ties this to AI chat histories, agent control panels, and provider dashboards; if the stolen cookie belongs to an operator/admin, the adversary may view sensitive conversations or reconfigure the agent.
- **AML.T0113 — Steal Web Session Cookie** *(newly cited)* (tactic: Credential Access). The theft step feeding AML.T0091.001 above — from browser storage, process memory, network traffic, or via injected JavaScript / unsafe LLM-output rendering; explicitly ties to AI chat interfaces, agent dashboards, and model-management consoles as targets.
- **AML.T0132 — Misconfigured or Publicly Exposed AI Services** *(2026.09 addition)* (tactic: Initial Access). Missing authentication in an LLM runtime or overly permissive public-access settings on an agent/SaaS deployment, discoverable via OSINT and active scanning. Directly matches a common real-world finding pattern (unauthenticated access to agent tools/configuration) and is worth testing explicitly as its own scenario rather than assuming it's covered by generic "credential abuse" testing. Secondary category: cross-referenced under ASI04 below.
- Cross-reference **AML.T0053 — AI Agent Tool Invocation** (primary ASI02, above) — its Privilege Escalation tactic tag makes it equally relevant here when the test is specifically about authority/entitlement rather than the mechanics of the tool call itself.

A genuinely open gap remains: none of the above directly names *authorization-propagation failure* (caller's actual entitlement vs. the agent's own broader service credential) as its own technique — that pattern is still closer to a classical access-control flaw than an AI-specific ATLAS technique, even after this expansion pass added T0012, T0091, T0113, and T0132. Worth re-checking the live matrix's Privilege Escalation/Credential Access tactics periodically in case a more specific technique is added.

**Cross-references from other categories:** **AML.T0011.002 / .003** (primary ASI02, above) — not directly identity-relevant enough to warrant a secondary-category cross-ref here (neither lists ASI03). **AML.T0057 — LLM Data Leakage** (primary ASI06, below) — secondary category ASI03, since leaked data commonly includes credentials/PII reachable through other users' sessions. **AML.T0081 — Modify AI Agent Configuration** (primary ASI10, below) — secondary category ASI03, since disabling security controls is itself a privilege-abuse vector. **AML.T0085 — Data from AI Services** and **AML.T0085.000/.001** (primary ASI02, above) — secondary category ASI03 for the "agent reaches data/tools a human caller couldn't" confused-deputy framing. **AML.T0112.000 — Local AI Agent** (primary ASI10, below) — not independently secondary-tagged ASI03, no cross-ref needed.

## ASI04 — Agentic Supply Chain Vulnerabilities

- **AML.T0010 — AI Supply Chain Compromise** (tactic: Initial Access). Gaining initial access by compromising a distinct part of the AI supply chain — hardware, data/annotations, the AI software stack, or the model itself. Sub-techniques below detail each vector individually (this was one of the systematic gaps found this session — the old file mentioned "sub-techniques T0010.000-.003" in prose but never cited them by name):
  - **AML.T0010.000 — Hardware** (tactic: Initial Access). Tampering with the physical GPU/TPU/embedded-device supply chain an AI system runs on — limited black-box testability for this skill, but a genuine sub-vector to note as untested/out-of-scope in a Phase 3 plan rather than silently assumed covered.
  - **AML.T0010.001 — AI Software** (tactic: Initial Access). Compromising AI-specific software packages (PyTorch, TensorFlow, LangChain, inference engines, AI DevOps tools) or their dependency chains — via namesquatting, compromising legitimate packages, targeting LLM-hallucinated package names (see AML.T0060 under ASI08), or an AI Supply Chain Rug Pull (AML.T0109, below).
  - **AML.T0010.002 — Data** (tactic: Initial Access). Compromising training/fine-tuning data sources, including the labeling pipeline itself (an outside labeling service's output can be poisoned at the annotation stage) — overlaps with Training Data Poisoning (AML.T0020, ASI06) as the delivery mechanism.
  - **AML.T0010.003 — Model** (tactic: Initial Access). A compromised open-source foundation or fine-tuning-base model, often requiring execution of a saved-model file at load time — the base for a deployed agent being compromised before the organization ever touches it.
  - **AML.T0010.004 — Container Registry** (tactic: Initial Access). Pushing a manipulated container image that overwrites an existing image name/tag, pulled automatically by CI/CD pipelines or developers — may itself bundle a manipulated AI model (AML.T0018 below).
  - **AML.T0010.005 — AI Agent Tool** (tactic: Initial Access). Compromised MCP servers / agent tools as the named agentic-specific supply-chain vector — the description explicitly cites a real-world incident of a poisoned MCP server used to exfiltrate private user data. Secondary category: cross-referenced under ASI02 above.
- **AML.T0110 — AI Agent Tool Poisoning** (tactic: Persistence). Poisoning a tool's model-visible definition, executable implementation, or runtime responses — the registration/definition-time counterpart to ASI02's invocation-time T0011.002. Three sub-techniques (all newly broken out this pass — the old file cited only the parent):
  - **AML.T0110.000 — Definition and Instructions** (tactic: Persistence). Poisoning the tool's model-visible description/docstring/schema/annotations — the specific, well-documented MCP "tool poisoning" and "tool shadowing" mechanism, where a malicious tool's definition can influence how the agent invokes a *different*, trusted tool once both definitions share the same model context, even without the malicious tool ever being invoked.
  - **AML.T0110.001 — Implementation** (tactic: Persistence). Poisoning the tool's executable backend so normal-looking invocation produces hidden side effects (e.g. an email tool that silently BCCs an adversary address) — does not require the model to interpret any malicious instruction; the poisoned behavior is pure code. Can persist in already-installed copies even after the malicious source is taken down.
  - **AML.T0110.002 — Runtime Response** (tactic: Persistence). A malicious/compromised tool deliberately returning poisoned content (fake instructions, deceptive data, fabricated errors) into the agent's context after an otherwise-approved tool call — a tool-mediated context-poisoning mechanism. Secondary category: cross-referenced under ASI06 below.
- **AML.T0084 — Discover AI Agent Configuration** (tactic: Discovery) and its sub-technique **AML.T0084.001 — Tool Definitions** (tactic: Discovery). Discovering what tools an agent has access to and how they're defined — the reconnaissance step behind a tool-description-mismatch or typosquat scenario. Additional sub-technique in this category: **AML.T0084.000 — Embedded Knowledge** (tactic: Discovery) — discovering what data sources/knowledge an agent can access, mapping high-value RAG/document targets for later exploitation. (Two further sub-techniques of T0084 — Activation Triggers and Call Chains — have primary categories elsewhere and are cited standalone under ASI01 and ASI05 respectively, with a note back to this parent.)
- **AML.T0111 — AI Supply Chain Reputation Inflation** (tactic: Defense Evasion). Building or leveraging credible-looking trust signals (established developer accounts, real download/star/fork counts, benign version history) to drive adoption of a malicious or compromised model/dataset/package/tool before swapping in the malicious payload — a direct match for the typosquat/lookalike-via-fake-legitimacy scenario.
- **AML.T0109 — AI Supply Chain Rug Pull** *(newly cited)* (tactic: Defense Evasion). Publishing a legitimate component, building adoption (often via Reputation Inflation, above), then pushing a malicious update — the specific mechanism that lets a component bypass the extra scrutiny typically applied only at first adoption.
- **AML.T0074 — Masquerading** *(newly cited)* (tactic: Defense Evasion). Manipulating an artifact's name/metadata to appear legitimate; the current description specifically calls out reclaiming a deleted or renamed namespace on a model/artifact registry (e.g. HuggingFace) so that systems resolving a stale, unpinned identifier retrieve an adversary-controlled artifact believed to be the original.
- **AML.T0018 — Manipulate AI Model** *(newly cited)* (tactic not resolved in this file's source pull — verify against the live matrix). Manipulating a model artifact or its bundled prompt-construction logic to change system behavior, introduce malicious code, or establish persistence — may retain expected behavior under ordinary conditions while activating malicious behavior only under selected inputs/contexts. Four sub-techniques:
  - **AML.T0018.000 — Poison AI Model** (tactic: AI Attack Adaptation, Persistence). Directly manipulating model weights, or training/fine-tuning on poisoned data, to bias behavior toward targeted topics/facts or general degradation. Secondary category: cross-referenced under ASI06 below.
  - **AML.T0018.001 — Modify AI Model Architecture** (tactic: Persistence). Adding/removing layers or pre/post-processing steps — can remove class-prediction ability, inflate compute cost, or inject an adversary-defined sub-network as an input-conditional backdoor into the computation graph.
  - **AML.T0018.002 — Embed Malware** (tactic: AI Attack Adaptation). Malicious code embedded in an unsafe model-file format (e.g. pickle's `exec` capability) that executes on load, even while the model still "works." Secondary category: cross-referenced under ASI05 below.
  - **AML.T0018.003 — Modify Prompt Construction Logic** (tactic: AI Attack Adaptation). Tampering with bundled templates, role delimiters, system instructions, or tool-call formatting packaged inside a model artifact (e.g. GGUF) — a persistent, weights-independent supply-chain route to goal hijack, since a compatible runtime reinterprets the tampered logic on every future inference. Secondary category: cross-referenced under ASI01 above.
- **AML.T0076 — Corrupt AI Model** *(newly cited)* (tactic: Defense Evasion). Deliberately corrupting a malicious model file so it fails deserialization — evading a model scanner — while still executing its malicious payload *before* the deserialization failure occurs.
- **AML.T0112.001 — AI Artifacts** (tactic: Impact; standalone — sub-technique of AML.T0112, "Machine Compromise," cited under ASI05). Malware embedded in a model/data artifact pulled from a registry causing full system compromise via unsafe serialization (pickle) or bundled notebooks/scripts. Secondary category: cross-referenced under ASI05 below.
- **AML.T0132 — Misconfigured or Publicly Exposed AI Services** (cross-reference — primary category ASI03, above; see that entry for full description). Secondary category here because a misconfigured/exposed deployment is itself a supply-chain-adjacent exposure of the agentic stack.
- **AML.T0122 — Exploitation of Remote Services** *(newly cited)* (tactic: Lateral Movement). Exploiting a weakness in a reachable service to cross a trust boundary — explicitly lists AI-specific remote services as targets: vector databases, inference gateways, model/artifact registries, evaluation infrastructure, experiment trackers, notebooks, training pipelines, and cloud/cluster control planes, several of which may be reachable from an otherwise-isolated agent workload. Secondary category: cross-referenced under ASI05 below.
- **AML.T0133 — Discover AI Agent Runtime Capabilities** *(2026.09 addition)* (tactic not resolved in this file's source pull — verify against the live matrix). Mapping an agent's tools, permissions, and identity purely through runtime interaction — varied requests and observing success/failure/refusal — without needing configuration access. Explicitly named as the mapping step that precedes AML.T0053 exploitation; this is close to how this skill's own Phase 1/2 reconnaissance actually operates, so a Phase 3 plan should treat this technique's completeness (did we map the *full* toolset, not just the obvious tools?) as its own checklist item.
- Upstream/staging steps, not standalone live tests: **AML.T0002.002 — AI Agent Configuration** (tactic: Resource Development) — acquiring exposed MCP/agent configuration files (system prompts, tool configs, credentials) as a direct supply-chain recon step; **AML.T0016.004 — AI Agent Tools** (tactic: Resource Development) — obtaining/configuring a malicious MCP server or agent tool for deployment against a victim; **AML.T0017.002 — AI Agent Tools** (tactic: Resource Development) — *developing* (rather than obtaining) a malicious/poisoned MCP server or tool integration; and the **AML.T0115 — Publish Poisoned AI Artifacts** family (tactic not resolved in this file's source pull — verify against the live matrix), the publishing step that feeds AML.T0010 downstream, with three sub-techniques by artifact type: **AML.T0115.000 — Datasets** (tactic: Resource Development), **AML.T0115.001 — Models** (tactic: Resource Development), and **AML.T0115.002 — AI Agent Tools** (tactic: Resource Development, citing real-world open registries like npm and MCP-specific hubs as largely unregulated distribution channels).

It does not appear as a technique name anywhere in the current 208-entry ATLAS technique catalog — it could not be verified and should not be cited. Dropped. (AML.T0110 and AML.T0010.005, above, are the correct current IDs for this territory.)

**Cross-references from other categories:** **AML.T0011.000 — Unsafe AI Artifacts**, **AML.T0011.001 — Malicious Package**, **AML.T0011.002 — Poisoned AI Agent Tool** (all primary ASI05/ASI02, cited there) — each has ASI04 as a secondary category since they all describe supply-chain-delivered artifacts. **AML.T0043.004 — Insert Backdoor Trigger** (primary ASI06, below) — secondary category ASI04, since it's typically paired with model poisoning delivered via the supply chain.

## ASI05 — Unexpected Code Execution (RCE)

- **AML.T0050 — Command and Scripting Interpreter** (tactic: Execution). Abusing a command/script interpreter tool reachable from the agent to execute commands, scripts, or binaries.
- **AML.T0011 — User Execution** (tactic: Execution). Relying on a user (or, in agentic context, the agent's own automatic execution path) to load/execute a malicious artifact — introduced via AI Supply Chain Compromise (ASI04) or classic social engineering (a malicious document or link). Sub-technique in this category:
  - **AML.T0011.000 — Unsafe AI Artifacts** (tactic: Execution). Malicious model/template/tokenizer bundles that execute or alter agent behavior when loaded — may exploit a deserialization vulnerability for host code execution, or may simply abuse intentionally-supported runtime functionality to alter context, outputs, safety behavior, or agent actions without any traditional "exploit" at all. Secondary category: cross-referenced under ASI04 above.
- **AML.T0102 — Generate Malicious Commands** (tactic: AI Attack Adaptation). Using an LLM to dynamically generate malicious commands from natural language — relevant when the agent's own code-generation feeds a downstream execution sink; the description cites a real campaign (APT28/LAMEHUG) using a HuggingFace-hosted model for this purpose.
- **AML.T0097 — Virtualization/Sandbox Evasion** (tactic: Defense Evasion). Relevant once a code-execution tool is confirmed reachable — detecting/evading the assessor's own sandbox (checking for VM artifacts, monitoring tools, hypervisor-specific MAC prefixes/registry keys/processes), which is exactly why SKILL.md requires that sandbox to be disposable and isolated by construction.
- **AML.T0105 — Escape to Host** *(newly cited)* (tactic: Privilege Escalation). Breaking out of a container/virtualized environment to reach the underlying host — the description explicitly connects this to AI agents: modifying an agent's configuration to disable safety features or user-confirmation prompts can itself be the escape vector, letting the agent invoke tools directly on the host rather than in a sandbox.
- **AML.T0049 — Exploit Public-Facing Application** *(newly cited)* (tactic: Initial Access). Classic public-facing-application exploitation (a bug, glitch, or design flaw in an internet-accessible service), directly applicable when the public-facing application *is* the agentic application/API itself, not just a downstream service it calls. Secondary category: cross-referenced under ASI02 above.
- **AML.T0112 — Machine Compromise** *(newly cited)* (tactic: Impact). Umbrella technique for full system compromise via AI-enabled components — this parent groups the two mechanisms below. (The Local AI Agent sub-technique has a different primary category and is cited standalone under ASI10.)
  - **AML.T0084.003 — Call Chains** (tactic: Discovery; standalone — sub-technique of AML.T0084, cited under ASI04, but its own mechanism is RCE-specific). Extracting call chains from agent-framework configuration that connect user input or LLM output to an execution sink (`exec`, `eval`, `os.popen`) — a direct, specific match for the injection-to-RCE sandbox-escape scenario, letting an adversary systematically find and target vulnerable frameworks rather than fuzzing blindly.
- **AML.T0017.001 — Autonomous Exploit Development** *(2026.09 addition)* (tactic: Resource Development; staging). An autonomous agent independently analyzing source, documentation, and error responses to formulate and test vulnerability hypotheses, then package a working exploit with limited human direction. Directly relevant to assessing what a goal-hijacked or rogue agent with code-execution tools and internet/repo access could develop unsupervised — this is a capability-development technique worth testing for (can the target agent be induced to do this against a third party?) as well as guarding against (could a rogue instance of the assessed agent itself do this?). Secondary category: cross-referenced under ASI10 below.
- **AML.T0119 — Exploit Automated Artifact Processing Pipeline** *(2026.09 addition)* (tactic: Initial Access). Submitting or modifying an artifact to exploit weaknesses in an *automated backend* processing pipeline — no human ever opens, loads, or approves the artifact; the worker itself is exploited using its own permissions. Distinct from AML.T0011 (User Execution) precisely because no user action is the trigger — relevant to any unattended document-ingestion, auto-summarization, or CI-triggered agent pipeline in the target's architecture. Secondary category: cross-referenced under ASI08 below.
- **AML.T0122 — Exploitation of Remote Services** (cross-reference — primary category ASI04, above; see that entry). Secondary category here because several of the listed AI-specific remote services (inference gateways, notebooks, training pipelines) are plausible RCE-adjacent targets once reached.
- **AML.T0123 — Obfuscated Files or Information** (cross-reference — primary category ASI01, above; see that entry). Secondary category here because obfuscation techniques used to smuggle a payload past an AI-based content/secret scanner are directly relevant to getting a malicious file past automated pre-execution screening.
- **AML.T0100 — AI Agent Clickbait** (cross-reference — primary category ASI01, above; see that entry). Secondary category here because a successful clickbait lure can directly lead the agent to copy and execute malicious code on the host.

**Cross-references from other categories:** **AML.T0011.001 — Malicious Package** and **AML.T0018.002 — Embed Malware** and **AML.T0112.001 — AI Artifacts** (primary ASI04, above) — each secondary-tagged ASI05 for the code-execution effect of a supply-chain-delivered artifact. **AML.T0076 — Corrupt AI Model** (primary ASI04, above) — secondary-tagged ASI05 for the same reason (scanner-evading model file that still executes).

## ASI06 — Memory & Context Poisoning

- **AML.T0080 — AI Agent Context Poisoning** (tactic: Persistence). Manipulating the context an agent's LLM uses, to persistently influence its future responses/actions — broader than RAG specifically, and a better primary match for this category than RAG Poisoning alone. Two sub-techniques (newly broken out this pass):
  - **AML.T0080.000 — Memory** (tactic: Persistence). Poisoning a persistent, cross-session memory feature via ordinary conversational phrasing ("remember my preference for...") delivered through direct or indirect prompt injection — the precise mechanism behind the "poisoned memory persists across sessions" test scenario.
  - **AML.T0080.001 — Thread** (tactic: Persistence). Poisoning within a single long-running thread/context window rather than a durable memory store; notes that rising context-window limits let malicious instructions persist longer, and that a shared-thread deployment (e.g. an agent active in a multi-user Slack channel) lets one user's poisoning affect the agent's behavior toward every other participant.
- **AML.T0070 — RAG Poisoning** (tactic: Persistence). Malicious content injected into RAG-indexed data to contaminate future retrieval-augmented answers; may be targeted to surface for a specific query, and may carry false/misleading information, embedded prompt injections, or false RAG entries.
- **AML.T0071 — False RAG Entry Injection** (tactic: Defense Evasion). Introducing false document entries into a RAG database designed to be interpreted as legitimate retrieved content — bypasses data-monitoring tools and resists deletion because it's nested inside a regular RAG entry; the adversary may also manipulate the injected entry's metadata (title, author, date) to look more credible.
- **AML.T0099 — AI Agent Tool Data Poisoning** (tactic: Persistence). Poisoning a data source reachable through an agent tool (document repository, database, source-code repo, search index) rather than through a dedicated RAG ingestion path — relevant when the poisoning route is a tool, not a RAG upload UI. Distinguished from a malicious tool that fabricates its own response (that's AML.T0110.002, ASI04) — here the *tool is faithful*, the *underlying data* is poisoned.
- **AML.T0020 — Training Data Poisoning** (tactic: Resource Development, Persistence). Compromising fine-tuning or foundation training data — adding, removing, or relabeling samples, or manipulating feedback/collection processes — to embed targeted errors, bias, or backdoors that persist in the trained model after the poisoned data is no longer accessible. Broader/older technique than the live-memory/RAG techniques above; relevant when the mechanism under test is model-level rather than a live store.
- **AML.T0018.000 — Poison AI Model** (tactic: AI Attack Adaptation, Persistence; standalone — sub-technique of AML.T0018, "Manipulate AI Model," cited under ASI04, but weight-level poisoning is functionally a memory/behavior-poisoning technique too). Directly poisoning model weights via manipulation, poisoned training, or targeted fine-tuning — the model-artifact-level analogue of context/memory poisoning, delivered via the supply chain rather than live interaction.
- **AML.T0043.004 — Insert Backdoor Trigger** (tactic: AI Attack Adaptation; standalone — sub-technique of AML.T0043, "Craft Adversarial Data," cited under ASI01). Inserting an imperceptible or non-obvious perceptual trigger into inference data, used alongside AML.T0018.000 so a specific keyword/pattern activates hidden poisoned behavior — a documented trigger-phrase backdoor pattern directly relevant to testing whether a target's guardrails or fine-tuning have such a dormant trigger. Secondary category: cross-referenced under ASI04 above.
- **AML.T0059 — Erode Dataset Integrity** *(newly cited)* (tactic: Impact). A softer, more generic technique — poisoning/degrading portions of a dataset specifically to reduce its usefulness and trust, causing users to waste resources correcting errors, rather than to plant a targeted backdoor; relevant as the "death by a thousand cuts" variant alongside the more surgical poisoning techniques above.
- **AML.T0057 — LLM Data Leakage** *(newly cited)* (tactic: Exfiltration). Prompts crafted to induce the LLM to leak sensitive information — from proprietary training data, from connected data sources, or (notably) from *other users'* sessions — genuinely LLM-native and distinct from the poisoning techniques above in that it's a read rather than a write. Secondary category: cross-referenced under ASI03 above.
- **AML.T0110.002 — Runtime Response** (cross-reference — primary category ASI04, above; see that entry). Secondary category here because a malicious tool fabricating its return content is, from the agent's perspective, indistinguishable from context poisoning delivered by any other channel.
- Upstream steps: **AML.T0064 — Gather RAG-Indexed Targets** (tactic: Reconnaissance) — identifying what data sources to poison, and **AML.T0066 — Retrieval Content Crafting** (tactic: Resource Development) — writing content designed to surface for unrelated queries and influence the reader; the adversary may use an LLM itself to help craft this content.

**Cross-references from other categories:** **AML.T0051.002 — Triggered** (primary ASI01, above) — secondary ASI06 for its role in evading turn-scoped context defenses. **AML.T0084.000 — Embedded Knowledge** (primary ASI04, above) — secondary ASI06 as the recon step mapping which knowledge sources are poisonable. **AML.T0093 — Prompt Infiltration via Public-Facing Application** and **AML.T0094 — Delay Execution of LLM Instructions** (primary ASI01, above) — both secondary ASI06 for their persistence-into-memory/RAG angle. **AML.T0077 — LLM Response Rendering** and **AML.T0085.000 — RAG Databases** (primary ASI02, above) — secondary ASI06.

## ASI07 — Insecure Inter-Agent Communication

- **AML.T0118 — Autonomous AI Agent Communication** (tactic not resolved in this file's source pull — verify against the live matrix). Autonomous agents exchanging operational information (discoveries, objectives, tasking, capabilities, credentials, constraints, targeting information) with other agents, sub-agents, or independent runs, without a human directing each interaction.
  - **AML.T0118.000 — Communication via Shared Artifacts** (tactic: AI Attack Adaptation). Communication indirectly via a shared resource (file, queue, board, object store, database) that persists outside any single agent's execution context — agents don't need to share a model, orchestrator, or overlapping execution period.
  - **AML.T0118.001 — Direct Agent Communication** (tactic: AI Attack Adaptation). Direct agent-to-agent, sub-agent, or orchestrator-interface messaging, including delegation (where the recipient retains discretion over how to perform a sub-task) as well as non-delegated reporting/validation/synchronization exchanges.
- **AML.T0124 — Autonomous Attack Orchestration** *(2026.09 addition; staging)* (tactic: AI Attack Adaptation). A centralized autonomous system managing multiple distinct agents/sub-agents toward a shared objective — assigning work, allocating resources, reconciling conflicting results, reassigning stalled work — without a human directing each assignment. Distinct from attack-path adaptation (AML.T0117, ASI10) in that orchestration is about *how work is allocated and coordinated across agents*, not how one agent's own path evolves; directly relevant to testing a multi-agent deployment's trust boundary between an orchestrator and its sub-agents (can a sub-agent's poisoned output redirect what the orchestrator assigns next?). Secondary category: cross-referenced under ASI10 below.

This directly supports all three ASI07 example scenarios (unauthenticated participation, instruction smuggling via peer message, message replay/spoof) — apply each against whichever of T0118.000/T0118.001 matches the actual channel shape, and use T0124 specifically for orchestrator-trust-boundary scenarios in a multi-agent deployment.

**Cross-references from other categories:** **AML.T0061 — LLM Prompt Self-Replication** (primary ASI01, above) — secondary ASI07 for the payload-propagates-to-other-agents angle. **AML.T0084.002 — Activation Triggers** (primary ASI01, above) — secondary ASI07 for unauthenticated-peer-triggering scenarios (discovering what makes an agent respond to another agent's message).

## ASI08 — Cascading Failures

- **AML.T0060 — Publish Hallucinated Entities** (tactic: Resource Development). An adversary creates a real entity (package, website, email) matching something an LLM hallucinated, so a later consumer treating the hallucination as verified fact reaches attacker-controlled infrastructure — a strong, concrete match for the "fabrication propagation" scenario.
- **AML.T0062 — Discover LLM Hallucinations** (tactic: Discovery; staging). Reconnaissance step of prompting a target LLM to find what it hallucinates — the step that precedes T0060; different LLMs have been shown to share the same hallucinations, so hallucinations discovered against one model may affect users of others.
- **AML.T0034 — Cost Harvesting** (tactic: Impact) and its sub-technique **AML.T0034.002 — Agentic Resource Consumption** (tactic: Impact). Deliberately driving an AI service beyond normal capacity to inflate cost — via high-volume/low-complexity queries (**AML.T0034.000 — Excessive Queries**, tactic: Impact — exploiting rate limits, autoscaling, and pay-per-use billing), low-volume/high-complexity queries (**AML.T0034.001 — Resource-Intensive Queries**, tactic: Impact — long inputs, extremely long output requests, "sponge examples" maximizing energy/latency), or (the agentic-specific sub-technique) coercing an agent into computationally expensive tool calls via T0051 (prompt injection) or T0099 (tool data poisoning) — including agentic self-delegation loops that force the agent to recursively delegate to itself, causing stack overflows and resource exhaustion. Matches the cost/telemetry evidence requirement this category needs.
- **AML.T0029 — Denial of AI Service** (tactic: Impact). Flooding an AI-enabled system with requests, or crafting inputs that force heavy useless compute, to degrade or shut down the service — the outright-availability counterpart to T0034's cost-inflation angle.
- **AML.T0031 — Erode AI Model Integrity** *(newly cited)* (tactic: Impact). Degrading target-model performance with adversarial inputs specifically to erode confidence in the system *over time* — the victim organization wastes time/money both trying to fix the system and manually performing the task it was meant to automate; a slower-burn cascading-failure variant distinct from an outright DoS.
- **AML.T0046 — Spamming AI System with Chaff Data** *(newly cited)* (tactic not resolved in this file's source pull — verify against the live matrix). The current description explicitly covers spamming AI *agents* with excessive low-severity auditable events or actions requiring human-in-the-loop review — a direct match for an "approval fatigue" scenario where a flood of low-stakes confirmations desensitizes a human reviewer to a later high-stakes one. Secondary category: cross-referenced under ASI09 below.
- **AML.T0119 — Exploit Automated Artifact Processing Pipeline** (cross-reference — primary category ASI05, above; see that entry). Secondary category here because an exploited unattended pipeline is itself a cascading-failure vector (one poisoned artifact silently corrupts everything the pipeline subsequently touches).

**Cross-references from other categories:** none beyond AML.T0119 noted above.

## ASI09 — Human-Agent Trust Exploitation

- **AML.T0067 — LLM Trusted Output Components Manipulation** (tactic: Defense Evasion). Manipulating components of an LLM's response specifically to make it *appear trustworthy* to the human reading it — a direct match for the "deceptive summary check" scenario; covers tailored language, links, recommended follow-up actions, and retrieved-document metadata.
  - **AML.T0067.000 — Citations** (tactic: Defense Evasion). Providing a wrong citation, a fabricated citation, or a real citation attached to adversary-provided data — concrete enough to be its own test variant.
- **AML.T0073 — Impersonation** (cross-reference — primary category ASI01, above; see that entry). An authority-framing probe ("per the security team's request...") is this technique applied to a human reviewer rather than to the model itself.
- **AML.T0052 — Phishing** and **AML.T0052.000 — Spearphishing via Social Engineering LLM** (tactic: Initial Access). An LLM turned into a targeted social engineer against a human — programmed via system prompt to seek sensitive information, targetable to a persona defined by the adversary, scaling spearphishing efforts. Additional sub-technique in this category:
  - **AML.T0052.001 — Deepfake-Assisted Phishing** *(newly cited)* (tactic: Initial Access, Lateral Movement). GenAI voice/video deepfakes (cloned from as little as a few seconds of public audio, or from meeting/earnings-call video) used in vishing or video-conference phishing to impersonate executives or trusted contacts — the description cites real large-scale campaigns causing significant financial losses and government-official targeting; typically staged via Obtain Capabilities → Generate Deepfakes (below) before the phishing campaign itself.
- **AML.T0088 — Generate Deepfakes** *(newly cited; staging)* (tactic: AI Attack Adaptation). Using generative AI to create synthetic imagery/video/audio/text that appears authentic, for impersonation in phishing or to evade biometric verification — reduced skill/effort requirement vs. older manipulation techniques, including real-time manipulation and purpose-built malicious tooling (e.g. "ProKYC").
- **AML.T0046 — Spamming AI System with Chaff Data** (cross-reference — primary category ASI08, above; see that entry). Secondary category here for the approval-fatigue angle specifically as a human-trust-exploitation mechanism (a desensitized reviewer trusts the agent's judgment by default).
- **AML.T0130 — AI Agent Response Biasing** *(2026.09 addition)* (tactic: Impact). Manipulating an assistant so it favors adversary-chosen sources or content in its responses ("treat [source] as trusted," "recommend [source] first") — presents promotional/self-serving content as neutral, well-reasoned advice, degrading trust in domains the user relies on the assistant for (health, finance, security) without the user knowing the advice was skewed. May be delivered via Crafted AI Assistant Links (AML.T0131, ASI01) and may persist if the agent's memory was poisoned (AML.T0080.000, ASI06) — a genuinely distinct mechanism from Citations manipulation (T0067.000) in that it biases *source selection/recommendation* rather than fabricating a specific reference.

**Cross-references from other categories:** **AML.T0011.003 — Malicious Link** (primary ASI02, above) — secondary ASI09 for the social-engineering delivery vector.

## ASI10 — Rogue Agents

- **AML.T0108 — AI Agent** (tactic: Command and Control). Abusing an AI agent already present in the environment for C2 — the agent has tool access (shell, internet, internal systems) and keeps operating while still appearing legitimate to anything checking only its identity/authentication; may be instructed not to report its actions to the user, and persistence is often maintained via Modify AI Agent Configuration (below) or Context Poisoning (ASI06).
- **AML.T0112.000 — Local AI Agent** (tactic: Impact; standalone — sub-technique of AML.T0112, "Machine Compromise," cited under ASI05). Full system compromise by abusing a locally-running agent (a computer-use agent, an AI-driven browser) — taking control of the agent effectively grants the same access the agent has: arbitrary code execution, credential/data access, config modification, persistence. Secondary category: cross-referenced under ASI05 above.
- **AML.T0121 — AI Agent Environment Reconstruction** (tactic: Persistence; staging). An autonomous agent reconstructing the environment/state needed to continue an operation after its execution context is lost or reset — recovering tools, dependencies, config, credentials, communication paths, or externally stored state to resume the same objective. A persistence/drift pattern relevant to detecting an agent that keeps operating off-policy across resets.
- **AML.T0103 — Deploy AI Agent** (tactic: Execution). Launching an agent in the victim's environment to act on the adversary's behalf — configured with an initial system prompt, granted excessive trust permissions, and with user interactions disabled so its actions aren't blocked; notably represents a loss of control for the adversary too, once the agent is autonomous.
- **AML.T0081 — Modify AI Agent Configuration** *(newly cited)* (tactic: Defense Evasion, Persistence). Modifying an agent's configuration file to persist malicious change beyond a single agent instance — tampering with the system prompt, knowledge sources, connected-tool settings, or (specifically called out) disabling a security control that would otherwise require human-in-the-loop approval for potentially harmful actions. Core to both rogue-agent persistence and identity-abuse testing. Secondary categories: cross-referenced under ASI03 and ASI06 above.
- **AML.T0096 — AI Service API** *(newly cited)* (tactic: Command and Control). Commands and results embedded in the normal traffic of a legitimate AI service API — covert because it blends into normal AI-service communications and lives off existing infrastructure; the description cites real-world use for stealthy, long-term-persistence espionage. Secondary category: cross-referenced under ASI02 above.
- **AML.T0114 — AI Service Web Interface** *(newly cited)* (tactic: Command and Control). Abusing a public AI assistant's *web interface* — via browser automation or an embedded WebView — as a covert relay: the malware prompts the assistant to fetch an attacker URL, embeds data in the request, and parses the assistant's response for instructions. Especially relevant where the AI web interface allows unauthenticated/anonymous browsing or summarization, since it avoids API-key- and account-based detection entirely, shifting detection to browser-automation and URL-fetch telemetry. Secondary category: cross-referenced under ASI02 above.
- **AML.T0120 — AI Artifact Repository** *(2026.09 addition)* (tactic: Command and Control). Repurposing an AI artifact/model registry as an asynchronous dead-drop C2 channel — commands placed in repository objects for a compromised system to poll, results written back via ordinary read/update operations, blending with legitimate artifact traffic. Secondary category: cross-referenced under ASI04 above.
- **AML.T0116 — Autonomous Reconnaissance** *(2026.09 addition; staging)* (tactic: Reconnaissance). An autonomous agent given an objective or partial lead that independently determines what to investigate and how, forming hypotheses, correlating sources, and revising scope without a human specifying each step — directly relevant to assessing what a goal-hijacked or rogue agent could independently discover and pursue unsupervised, including the risk of scope creep into unrelated/unauthorized systems. Secondary category: cross-referenced under ASI01 above.
- **AML.T0117 — Autonomous Attack-Path Adaptation** *(2026.09 addition; staging)* (tactic: AI Attack Adaptation). An agent that autonomously constructs and repeatedly revises an attack path toward an objective, incorporating observations to reprioritize, abandon branches, or pursue alternatives — notably, this can occur even while pursuing a *benign, authorized* objective, if the intermediate objectives the system selects cross a trust/safety boundary on their own. Directly relevant to behavioral-drift testing: does the agent's own planning process introduce harmful intermediate steps nobody explicitly asked for?
- **AML.T0017.001 — Autonomous Exploit Development** (cross-reference — primary category ASI05, above; see that entry). Secondary category here for what an unsupervised rogue agent instance could independently develop.
- **AML.T0124 — Autonomous Attack Orchestration** (cross-reference — primary category ASI07, above; see that entry). Secondary category here for the rogue-orchestrator framing (a compromised orchestrator directing otherwise-legitimate sub-agents).

**Cross-references from other categories:** **AML.T0112 — Machine Compromise** (primary ASI05, above) — secondary ASI10 as the umbrella for the Local AI Agent sub-technique cited here.

## General Reconnaissance / Capability-Development Staging (not mapped to a specific ASI category)

The 14 techniques below are genuinely AI/agentic-specific (not generic-infrastructure boilerplate) but describe reconnaissance or capability-acquisition steps an adversary takes *before* choosing which ASI category to attack — they don't correspond to a single OWASP ASI01-10 end-behavior on their own. They're listed here rather than force-fit into a category, per this file's input data's own judgment. A Phase 3 test plan should still be aware of them as the "how would an adversary even find/prepare to attack this" layer underneath whichever category-specific scenarios get selected.

- **AML.T0006 — Active Scanning** (tactic: Reconnaissance). Actively probing for publicly reachable AI systems and resources — the description specifically calls out scanning for AI DevOps tooling and probing whether an inbox is agent-managed. Four sub-techniques, all 2026.09 additions:
  - **AML.T0006.000 — Enumerate Hosted AI Resources** (tactic: Reconnaissance). Probing an agentic/SaaS platform's predictable URL structures (environment, tenant, resource-group, agent-name conventions) to discover live agents/endpoints a specific victim has deployed.
  - **AML.T0006.001 — Query Platform Metadata APIs** (tactic: Reconnaissance). Querying documented or undocumented control-plane/identity APIs on agentic SaaS platforms to uncover tenant/environment/deployment IDs — the description cites a real Entra ID/Power Platform OSINT tool that abused an undocumented API this way until authentication was added.
  - **AML.T0006.002 — Scan for Exposed AI Infrastructure** (tactic: Reconnaissance). Port/service scanning for self-hosted AI backends, model-serving endpoints, and agent infrastructure listening on predictable ports/paths, then fingerprinting the software stack and version for exploit targeting.
  - **AML.T0006.003 — Probe AI Agent Trigger Channels** (tactic: Reconnaissance). Sending crafted inputs to candidate public triggers (email addresses, webhooks, messaging channels) to elicit a response revealing agent-managed accounts and expose additional agentic attack surface for direct targeting.
- **AML.T0000.003 — Scan Databases** (tactic: Reconnaissance). Querying public internet-scan services (Shodan, Censys) to identify a victim's exposed AI infrastructure without any direct interaction with the target — purely passive, third-party-data-sourced, distinct from Active Scanning above.
- **AML.T0014 — Discover AI Model Family** (tactic not resolved in this file's source pull — verify against the live matrix). Fingerprinting which LLM/model family powers a target application — from documentation or via carefully constructed probing examples — to tailor jailbreak/injection payloads to that specific family's known weaknesses.
- **AML.T0040 — AI Model Inference API Access** (tactic: AI Model Access). Baseline legitimate access to a model's inference API — used to stage jailbreak/hallucination discovery and other attacks; notes that many systems share the same underlying foundation model, so vulnerabilities found via one application's API access can transfer to any other application built on the same shared model.
- **AML.T0024 — Exfiltration via AI Inference API** (tactic not resolved in this file's source pull — verify against the live matrix). General technique for exfiltrating private information via legitimate inference-API access — training-data membership inference, model inversion, or full model extraction. Falls outside the ASI01-10 agentic-behavior scope (closer to classic LLM Top 10 sensitive-information-disclosure/model-theft territory) but worth flagging if the assessment's scope includes model-confidentiality questions. Two sub-techniques:
  - **AML.T0024.000 — Infer Training Data Membership** (tactic not resolved in this file's source pull — verify against the live matrix). Inferring whether a specific sample was in the training set (or broader training-set characteristics) via shadow-model comparison or prediction-score statistics — a privacy-leakage technique, not an agentic-behavior one.
  - **AML.T0024.002 — Extract AI Model** (tactic: Exfiltration). Repeatedly querying the inference API to collect a labeled dataset sufficient to train a functional copy of the model — used to avoid per-query billing or to steal IP.
- **AML.T0005.001 — Train Proxy via Replication** (tactic: AI Attack Adaptation). The staging use of the same replication technique as T0024.002: building a proxy model from collected inferences specifically so the adversary can then craft and verify adversarial inputs offline before using them against the live target.
- **AML.T0016.002 — Generative AI** (tactic: Resource Development). Adversaries obtaining and often jailbreaking their *own* generative AI tooling (self-hosted via Ollama/vLLM, cloud-hosted, or via a hub like HuggingFace) to assist with malware generation, deepfakes, malicious commands, retrieval-content crafting, or phishing content — including a documented market in purpose-built "uncensored" models advertised for malicious use. This describes the attacker's own tooling rather than a target-application behavior, but is worth knowing about as the capability an adversary brings to bear against the target.
- **AML.T0008.005 — AI Service Proxies** (tactic: Resource Development). Commercial proxy services that resell access to frontier-model APIs, used to launder large-scale distillation/extraction traffic, malicious-command generation, or LLM-social-engineering content generation — infrastructure-layer staging that makes malicious traffic harder to attribute or block, including proxy infrastructure built from resold "LLM-jacked" victim accounts.

## Provenance note: on trusting secondary OWASP-to-ATLAS crosswalks

No official OWASP-published or MITRE-published crosswalk between the Agentic Top 10 (ASI01-10) and ATLAS techniques was found to exist as authoritative ground truth. A community-maintained one does exist (`GenAI-Security-Crosswalk`, `agentic-top10/Agentic_MITREATLAS.md`, header-attributed to "OWASP GenAI Data Security Initiative") and was checked against this file's authoritative ATLAS dataset before use. Result: of 23 technique IDs it cited, 15 were exactly correct, 4 were real techniques with cosmetically shortened/reordered names, and **4 cited a real ID that maps to a completely different, unrelated technique** — `AML.T0015` ("LLM Capability Escalation" claimed, actually "Evade AI Model"), `AML.T0040` ("Unsafe Deserialisation via LLM" claimed, actually "AI Model Inference API Access"), `AML.T0049` ("Spearphishing via AI" claimed, actually "Exploit Public-Facing Application" — the real spearphishing-via-LLM technique is the unrelated ID `AML.T0052.000`), and `AML.T0071` ("Embedding Manipulation" claimed, actually "False RAG Entry Injection"). Those four were rejected; `AML.T0010`, `AML.T0029`, and `AML.T0034` were independently verified correct and folded into ASI04/ASI08 above; the rest of that crosswalk's claims were not adopted.

**The lesson generalized, not just for this one file:** a polished attribution header (official-sounding maintainer, version number, changelog) is not evidence of accuracy on its own — every technique-ID claim from any secondary source, including future updates to this file, should be checked against the primary ATLAS dataset (`dist/v6/ATLAS-<latest>.yaml` in `github.com/mitre-atlas/atlas-data`) before being relied on in a report. Distinguish three trust levels explicitly rather than treating them as equivalent: (1) MITRE's own primary data — authoritative; (2) a secondary crosswalk's specific claims — must be independently verified per-claim, as demonstrated above; (3) which OWASP category a verified technique belongs under — this is this file's own semantic judgment, not a verified fact, since no reliable authoritative crosswalk for that specific linkage exists. This file's own 2026.09 expansion pass is itself an instance of (3): a rigorous, full-text-audited judgment call, but a judgment call nonetheless — a future maintainer disagreeing with a specific category placement should feel free to move an entry, provided they say so explicitly rather than silently.

## How to use this in Phase 3

For each OWASP category marked `applicable`: after selecting scenarios from `owasp-agentic-top10.md`, check this file's list for that category. If it names more than one distinct technique, the test plan should attempt more than one — proving a category's mechanism with a single technique (e.g., one injection payload in a `.txt` file) is not the same as covering the category's documented technique variety (e.g., PDF hidden text, OCR-image text, audio transcription, multimodal-metadata triggers, DAN-style jailbreak vs. fictional-framing jailbreak vs. multi-turn Crescendo escalation). Where this file says a category's ATLAS coverage is unconfirmed or a gap (tactic "not resolved," or an ID marked as needing live-matrix verification), say so explicitly in the Phase 3 test plan and Phase 5 report rather than silently treating the category as fully covered by OWASP alone.

Sub-technique nesting matters for coverage claims specifically: if a report says "ASI01 (Prompt Injection) tested," check whether the test actually exercised more than one of T0051.000 (Direct), T0051.001 (Indirect), and T0051.002 (Triggered) — these are meaningfully different attack surfaces (a direct user-turn payload vs. a hidden payload in retrieved content vs. a dormant payload that only fires on a future event), and a single passing/failing test against one doesn't generalize to the others. The same logic applies to every other technique broken out into sub-techniques below (T0010, T0011, T0018, T0034, T0051, T0052, T0067, T0069, T0080, T0084, T0085, T0091, T0110, T0112, T0115, T0118, and the staging-only T0006/T0024 families) — treat "the parent technique's category is covered" and "every relevant sub-technique's specific mechanism was tested" as two different claims, and don't conflate them in a report.

**On "tactic not resolved in this file's source pull":** the ATLAS structured dataset's per-technique records don't carry a direct tactic field — tactic association only exists in a separate relationships graph tied to specific real-world case studies, and not every technique has a documented case-study occurrence to derive a tactic from. Where this file states a tactic, it was resolved either directly from a matching case-study relationship in the 2026.09 dataset, or (for a handful of newly-added entries lacking any case-study occurrence, or where a sub-technique's own tactic couldn't be independently confirmed) inherited from the sub-technique's parent as a reasonable default, consistent with ATLAS's ATT&CK-style convention that sub-techniques generally share their parent's tactic. Where neither was possible, the entry is marked "not resolved" rather than guessed. In all cases the technique ID, name, and description are still directly sourced and accurate; only the tactic label needs a live-matrix check before citing it in a report.
